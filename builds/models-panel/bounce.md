## Detection rules break on the real catalogs

- **`grok-prev` gets a false update, or every family match is undefined.** The plan never says whether a "family" is the registry key or the family derived from the current id. `models.default.json:12` has `grok-prev: grok-4.5`. Derive from the id and grok-prev is proposed `grok-4.7` on day one. Match on the key and `grok-prev` never matches the catalog family `grok`, so it has no display name and no updates. The registry needs a per-family rule for pinned-previous families, and the plan needs to state which matching it means.
- **Criterion 3 ("zero candidates") is false today for grok.** `~/.grok/models_cache.json:10` lists `grok-4.7`, described as the latest frontier model, and the registry has `grok-4.6`. Unless the bump branch also bumps grok (unverified, no shell here), a real candidate exists on merge day. The escape hatch "listed and explained" lets any result pass. Write the expected candidate set out explicitly instead, per family, so a wrong parser can't hide behind an explanation.
- **Codex trailing-word family mapping yields numeric families.** `gpt-5.5` (`models_cache.json:754`) has trailing word `5.5`. `codex-auto-review` (line 834) yields `review`. Hidden filtering catches the second but not the first. The normaliser must return family `null` when the trailing word is numeric, and criterion 2 has no fixture for it.
- **No version fixture separates numeric from lexical compare.** Every listed fixture passes under string comparison. Add `5.10` vs `5.6` and `claude-opus-5-10` vs `claude-opus-5-9`.
- **Claude `min_claude_code_version` is ignored.** `claude-opus-5-5` requires `2.1.280` (catalog line 1). Proposing an id the installed CLI refuses is a proposal that breaks every skill on Accept. The harness module already probes versions via `readVersion`. Gate or annotate the candidate with it.
- **Codex's own `upgrade` block is ignored.** `models_cache.json:791-795` carries `upgrade.model` and `retirement_at` for `gpt-5.5`. That is the vendor's authoritative "this id is retiring" signal, and it crosses families, which the version heuristic never will. At minimum surface retirement dates for a current registry id.
- **A current id that has vanished from the catalog is never flagged.** The plan warns only on edit (plan line 63). The standing state "your pinned id is no longer offered" is the more useful alert and is missing.
- **Multiple Claude catalogs are unhandled.** The glob `*-cc.json` matches one file today, named by what looks like an account uuid. A second login creates a second file. Say which wins (newest `fetchedAt`).
- **Codex seats with private homes go permanently stale.** The plan reads only `~/.codex/models_cache.json`. `lib/usage/seats.js:16-31` moves seats out of `~/.codex`, and shortcuts export `CODEX_HOME`. After a move, "run codex once to refresh" never clears the note. Read every registered codex seat home and take the newest.
- **Grok `info.hidden` (line 30) and `renewed_at` (line 3) are not normalised.** Age should use `renewed_at`. Minor.

## Writes and sidecars

- **Merged-registry write-back is the likely builder bug and no criterion catches it.** If the edit route writes `loadRegistry().registry` to the user file, all nine families become pinned overrides and shipped default bumps stop applying. Criterion 6 only checks the edited key. Add: after editing opus, the user file's `models` contains exactly one key, and `assist` overrides survive untouched.
- **A second backup mechanism instead of the shadow history repo.** Every other ACS write goes through `history.recordBaseline` and `history.record` (server.js:536-549). `historyRelPath` accepts any path under HOME (paths.js:72-76), so nothing prevents using it. `backups/models/` also sits beside the existing `backups/model-registry-*` format from `tests/models-backup.mjs:55`. Two conventions for one directory.
- **Sidecar Accept bypasses the mtime conflict check.** PUT /api/file refuses to clobber an external edit (server.js:516-523). The strip writes `settings.json` and `config.toml` with no such check.
- **"Byte-identical except the key" needs a positional text edit, and the plan doesn't say so.** JSON parse and stringify changes whitespace. A string replace of the quoted old id also hits a top-level `"model": "<old id>"` value in the same file. Criterion 8 is correct but the design doesn't determine an implementation that meets it.
- **Renaming a `modelSettings` key carries per-model tuning onto a different model.** Real `~/.claude/settings.json:71-74` holds `claude-opus-5-5: { effortLevel: medium }`. The catalog shows opus-5-5 defaults to medium and opus-5 to high, so the setting is model-specific. Rename vs copy vs show-only is a judgment call for Cris, not for the builder.
- **The strip's mapping rule is undefined.** `sidecars()` (models.js:292-325) only knows "not a current value". It cannot say which family a `config.toml` `model =` line belongs to. Real `~/.codex/config.toml:1` is `gpt-6-sol`, which is ahead of the registry's `gpt-5.6-sol` today. A "propose registry value" strip would propose a downgrade. State that the strip is computed from the single edit (old id to new id), never from the general stale scan.
- **Edit validation lacks a vendor check.** `opus` set to `gpt-6-sol` passes `ID_RE`, is found in the Codex catalog, and gets no warning. The plan says "that vendor's catalog" but nothing records a family's vendor. Derive it from the current id prefix and refuse a prefix change without confirm.
- **No refusal rule when the user file is malformed.** Criterion 1 shows `registryError`. What an edit does then, overwrite or refuse, is unspecified. Overwrite silently drops the user's other overrides.

## Tests, guards, and runtime

- **Criterion 10 is unpassable as written.** It hashes all of `~/.claude` and `~/.codex`. The Claude Code session doing the build writes `~/.claude/projects/*.jsonl` continuously, and any running codex rewrites `models_cache.json`. `tests/real-home.mjs:16` hashes three narrow roots for this reason. Name the exact files: `settings.json`, `config.toml`, the three catalogs. Otherwise the builder narrows it quietly or the suite is red for unrelated reasons.
- **Criterion 3 in the suite makes verify.sh nondeterministic.** A "zero candidates against the real catalogs" assertion fails the day a model ships, which is the feature's purpose. Keep it a reported step, not a suite assertion.
- **QA criteria 6 and 7 on the live server mutate real config.** Editing opus and accepting a candidate against the live HOME changes `model-id opus` for every skill and writes real backups. Either run QA against a server started with a temp HOME or state that live mutation plus reset is accepted.
- **The 24h timer hangs tests unless unref'd, and does nothing useful without SSE.** If detection lives in `createApp` (server.js:221), every route test keeps a live timer. And a timer that re-reads files without calling `broadcast` (server.js:177) never updates an open tab's badge. Either drop it or wire it to SSE.
- **Where-used has no existing callsite logic to reuse.** `lint()` returns pattern hits, not per-family callsites, and flags bare `$(model-id x)` as a defect (models.js:194). `lintScope` (models.js:246-256) excludes CLAUDE.md, and `~/.claude/CLAUDE.md` is explicitly deferred (line 241). A where-used regex on a bare family name like `opus` or `sol` false-positives on prose. Anchor it to `model-id <family>`.
- **Where-used on every `/api/models` call is on the boot path for the badge.** `projectReviewConfigs` walks `~/Documents/Projects` to depth 6 (models.js:216-233). Put the pending count in the existing boot payload and compute where-used lazily.
- **The new guard should match the `child_process` specifier, not call names.** `CALL_RE` (guards.mjs:178) misses `execSync`, `execFileSync`, and `fork`. Guard b already trips on any listed call in an unlisted lib file (guards.mjs:326-330), so the plan's guard adds nothing unless it scans stripped source for the module specifier and dynamic imports.
- **Secret test misses the filename.** Criterion 4 plants markers in four fields. The Claude catalog's filename carries an account-looking uuid, and the Codex file carries full system prompts under `model_messages`. Plant a marker in the fixture filename and assert no catalog path appears in any response.

Two factual corrections to the plan text: the buttons at `index.html:48-52` are in the footer statusbar, not a top bar, and the view list at plan line 29 omits the `usage` view (`app.js:331`), which is the closest analogue with a refresh timer and POST routes. Also the Claude catalog carries no `identity`, `auth_method`, `origin`, or `etag` at all; only Codex and Grok do.
