# PR: merging main into a reviewed branch needs no re-review (review gate)

Decided by Cris 2026-11-05 from flags 2026-11-05-pr-413-…-964f4d and 2026-11-04-after-a-clean-rebase-…-722537. Fable's advisory (advisor.out in this folder) is the design source; read it first. Cris approved: trust content already on the default branch as seen through the local origin ref.

## Outcome
After a reviewed and closed branch merges in the default branch, the push gate needs no new model review for files only the default branch changed; a clean merge is re-closed (tests re-run) with zero model calls; files changed on both sides need only a slice review at the tip.

## Changes (review.mjs + skill text)
1. **Coverage base.** In `contentCover` (~3583), use the merge-base of the tip with the default branch as the base whenever it descends from the anchor review's baseSha; otherwise today's base. In `--gate` mode, where BASE is empty (~674), resolve the default branch read-only from `refs/remotes/origin/HEAD` (never run `remote set-head` in the hook); nothing resolves → today's behavior. The existing `blind`/`bothSides` rule keeps files changed on both sides uncovered until a record saw the merge.
2. ~~Close `base` to tracked configs~~ — already done (COMMAND_KEYS ~117, test X2). Instead: **one default-branch resolver** used by `contentCover` in every mode (gate, --summary, --tier-json, close): it reads only `refs/remotes/origin/HEAD`, requires it to be a symbolic ref under `refs/remotes/origin/` whose target exists, and never reads REVIEW_BASE/config `base` and never runs `remote set-head`. Detached, dangling or missing → today's behavior. The pre-push hook forwards the remote name (`$1`) to `--gate`; the new rule applies only when pushing to `origin`. The skill text states the trust: content on the local origin default-branch ref counts as reviewed.
3. **Re-close at a merge tip.** One helper: a merge commit whose other parents are all ancestors of the default branch counts as touching its `bothSides` files (conflict or auto-merged) PLUS every file whose merge-tip state differs from both parents' states (an "evil merge" edit is never hidden). Commits that are ancestors of the default branch are excluded from the commit range in both close call sites (~2713, ~2726) and from the push gate's riskPaths scan (~3721), so main's own commits never make the close partial or escalate risk. `--fix-check` at a merge tip diffs only branch-side content (files whose tip state differs from the default branch's), never main's whole delta. Tier/unjudged stats at a re-close measure from the new base. Use it where close checks commits after the review/fix check (~2713–2729) and in `touchedBetween` with `-m` (~2294). Clean merge → the existing review re-closes at the tip with the same status file. Conflicted merge → refuse with the existing message naming the both-sides files (the orchestrator slice-reviews them with REVIEW_PATHS at the tip and closes that slice).
4. **Messages**: the gate's uncovered note and close's refusal, when the only blockers are both-sides files of a base merge, say "re-close the existing review; slice-review these both-sides files at the tip" — never "close a review at the tip". Both refusal shapes (with and without a fix check) name the files.
5. **Skill text** (claude + codex twins): in the push-gate paragraph and rule 8 — update a reviewed branch by merging the default branch, never by rebasing; re-close the review at the merge tip; a both-sides file gets a slice review at the tip; replace "being on the remote already covers nothing" with "content already on the default branch needs no coverage".

## Acceptance criteria (tests in a new file beside review.coverage.test.mjs, pattern of its C3 test; tests create a real bare remote with main pushed and `refs/remotes/origin/HEAD` set, and run gate cases with REVIEW_BASE UNSET)
1. Branch A reviewed+closed; another branch B (touching other files) reviewed, closed and squash-merged into main; A merges main cleanly; re-close A's review at the merge tip → push gate passes; no reviewer stub call after the merge.
2. Same, but B changed a file A also changed (conflict resolved) → gate refuses naming only that file; a REVIEW_PATHS slice review + close of it at the tip → gate passes.
3. Merging a non-default branch (not an ancestor of origin/HEAD's branch) → its files stay uncovered.
4. Safety: REVIEW_BASE pointing at an unreviewed branch does not change the gate's base; origin/HEAD missing, detached or dangling → behaves as before and `git symbolic-ref refs/remotes/origin/HEAD` still fails afterwards (no set-head); pushing to a remote other than origin → old rule.
5. Evil merge: amend the merge commit to re-edit a reviewed branch-only file → close goes partial/refuses and the gate lists that file. Auto-merged both-sides file (different lines, no conflict) → still named.
5b. Variants: a clean fix check before the merge (the ~2726 path) re-closes cleanly; a sliced review re-closed at a merge tip works; main's squash touching a riskPaths file → the branch still passes with zero model calls.
5c. The refusal message for a both-sides-only case names the re-close; --summary and the gate agree on covered/uncovered for the same tip.
6. A rebase onto new main still needs coverage as today (no rebase equivalence).
7. No existing test assertion changes; `review.test.mjs` byte-identical; full suite passes.
