# /code-review — review → fix → one report

Review the committed diff for **code correctness** — bugs, regressions, edge cases, error handling, data integrity — judged against what the branch was supposed to do. **One review pass** by a reviewer from the pool; every HIGH and MEDIUM then goes straight to one fix round, without asking (rule 10 below). Fixes go to the builder subagent that wrote the branch, or I apply them in-context when no builder did — no loop.

Scope: code correctness vs. what was built. **Not** product direction. **Not** a security audit.

Why no loop: the loop's cost is re-reviewing the whole diff after every fix and re-spawning a fixer each round — that compounds to many minutes on a big diff. One review + one fix round is about one review's worth of time; the operator stays in control at the PR merge.

## Step 1 — Run the review (single pass, read-only)

Commit the work first, including the build folder (it reviews the committed diff vs the remote's default branch, auto-detected), then run the reviewer — **repo copy first, shared runtime as the fallback**:
```bash
REVIEW_SCRIPT=scripts/review.mjs
[ -f "$REVIEW_SCRIPT" ] || REVIEW_SCRIPT="$HOME/.agent-config-studio/review-gate/review.mjs"
node "$REVIEW_SCRIPT" "<intent: what the branch delivers, its acceptance criteria, and anything deliberately out of scope>"
```
Context comes from files: the orchestrator's plan via --plan <plan.md> or REVIEW_PLAN, the builder's adjacent log.md if present, and already-decided findings from the review log. Inside /build, pass the plan; a missing plan file refuses. The optional intent string can supplement those files. Decided stays decided: closed rejections on the same branch and repository are passed in as "already decided; don't re-raise without new evidence".
The repo's own scripts/review.mjs is the execution source when present. The first line names the copy and its path; an old copy that cannot log head is labelled and cannot cover a close.
- **Who reviews.** Reviewers come from the `reviewer` role in ACS (Models → Roles; `model-id --role reviewer --json`) — an unranked pool. Each family runs at its own flavor effort (`model-id --flavor <family> --json`), and its CLI follows its model id: `claude-…` → claude, `gpt-…` → codex, `grok-…` → grok. Families whose CLI is not installed are skipped, and one line names them. With no reviewer named, hard rules run first — `crossFamily`, then any config `force` rule (e.g. `{ "paths": ["**/auth/**", "**/payments/**"], "family": "<family>" }`, or `"paths": "risk"` for the `riskPaths` list) — then `pick` chooses: `first` (default, pool order), `rotate` (the family with the fewest logged reviews), a family name, or the command of an optional local classifier (it sees the diff's paths and line counts plus each family's flavor likes/quirks — never code; below confidence 0.7, or if it fails, the first family is used; its probabilities are printed and logged). `crossFamily: "prefer"` (default) skips pool members from the author's vendor when another remains — **pass `REVIEW_AUTHOR=<family or vendor that built the branch>`** when you know it; unknown, nothing is filtered and the run says so. The run prints one line naming the reviewer and why.
- **Routing by size.** With config `routing` set, e.g. `[{"maxLines": 150, "family": "<small-diff family>"}, {"family": "<everything else>"}]`, the first entry whose `maxLines` the diff's changed lines (added + removed) are under picks the reviewer, and an entry without `maxLines` takes the rest; a diff touching riskPaths is never small. Order: `REVIEW_REVIEWER` / `reviewer`, then a `force` rule, then a pick (`REVIEW_PICK` for one run, or config `pick`, which prints a note that it overrides routing), then routing. Routing ignores crossFamily, each family runs at its own effort, a family must be in the reviewer role, and fix checks route on the fix diff. A family no entry names (grok, say) reviews only when named. `--show-config` shows the route and why. With no `routing`, the pick decides as before.
- **Shadow reviewers.** Config `shadow` (or `REVIEW_SHADOW=<family>,…`; a tracked repo config can't set it) lists families that review the same diff after the real review, detached in the background, for comparison only: each writes one record to `review-log/shadow-log.jsonl`, linked by review id, and nothing else. A shadow never changes findings, statuses, a close, the push gate or `--summary`, and a shadow that fails or is refused (grok with MCP servers that would start) is a record, not an error. Reviews only, not fix checks. `node "$REVIEW_SCRIPT" --shadow-report [--since <date>]` prints, per shadow family, how many of its findings matched a real one (same file and a line within 5, or one quote containing the other), how many were its own, how many real findings it missed, and its average duration.
- **Shadow pickers.** Config `pickShadow` (or `REVIEW_PICK_SHADOW=<classifier>,<family>,…`; a tracked repo config can't set it, default off) lists pickers that each log, after the real review and detached, which reviewer family they would have chosen, how complex the diff is, and why: the configured `classifier` command on diff stats and paths, any other family through `ask-model --min-tools` with the capped diff from an empty temp folder (claude with no tools; grok and codex with the fewest their CLIs allow, each record's `tools` and `toolsNote` saying which). No flavor text reaches them. Each writes one `pick-shadow` record to `review-log/shadow-log.jsonl` and nothing else; reviews only. `node "$REVIEW_SCRIPT" --pick-report [--since <date>]` prints, per picker, runs, failures, agreement with the actual reviewer, the families and complexities it chose, and the tools it had.
- **Grok runs.** A grok review or shadow runs with an empty temporary HOME and the real GROK_HOME, so nothing grok borrows from `~/.claude` or `~/.cursor` (plugin MCP servers, hooks) starts, and its login is the usual one. It is refused while grok would still start an MCP server, run the project's hooks, or run in leader mode (set in any grok config layer or by macOS device management; a layer that can't be read counts as on). `grokMcpAllow` lists servers from grok's own `config.toml` that may start anyway (their tools stay denied): operator-only, in the home config or `REVIEW_GROK_MCP_ALLOW`, never a tracked repo config, and empty by default; ask-model reads the same key from the home config.
- **No silent fallback.** The run stops with a message naming the fix — never trying another vendor — when `model-id` is missing (`acs install-model-id`), the reviewer role is unset (you choose it at install: `acs packs install review-gate --set-role reviewer=<family>[,…]`), missing or broken, no family in the role has its CLI installed, or a reviewer you named has no CLI (ACS → Models → Roles).
- **Naming a reviewer** (`REVIEW_REVIEWER` or config `reviewer`) bypasses the pool: `codex` (the role's first codex family unless `REVIEW_MODEL` pins one), `claude` (the team), `grok`, or any family name. A config `model` alone also pins a codex reviewer; a raw model id there passes through as given.
- **Findings must be provably real.** Every finding carries a `quote` copied from the file. After the review a script checks the quote is in the file (at HEAD) starting within ±5 lines of the cited line, normalizing whitespace only. A finding that fails is marked `unverified-quote`, kept out of the findings, and listed under "could not be located in the code" (and counted in the log). Optional `verify: "second-opinion"` (`REVIEW_VERIFY=second-opinion`, off by default) sends only located, unfiled findings (skipping legacy reviewer-LOW findings) to one other pool family — another vendor when the pool has one — which answers CONFIRMED / REFUTED with one line of evidence; REFUTED findings move to a "disputed" section, never dropped. A verifier failure keeps every finding and warns.
- **Grok is read-only by tool allowlist** (`--tools read_file,list_dir,grep`) — its plan mode and `--disallowed-tools` do not stop writes, so the allowlist is the only guard. The run fails loudly if grok's `modelUsage` names no grok model.
- **Portable — configure, don't fork.** The same script runs in any repo. The base branch is **auto-detected** from `origin/HEAD`, so `staging`/`master`/`develop` repos need no setup; `REVIEW_BASE=origin/<branch>` still pins it for one run. If `origin/HEAD` can't be resolved it warns loudly before falling back to `origin/main` — never a silent wrong-base review. One gap it can't catch: an `origin/HEAD` that is set but *stale* (the remote renamed its default branch after you cloned) resolves silently to the old branch — the run banner prints the resolved base, so check it, and re-run `git remote set-head origin --auto` if it looks wrong.
- **Optional per-repo gate.** Set `verifyCmd` in `.claude/review-config.json` (e.g. `"npm run type-check"`) and it runs *before* the reviewer, with its pass/fail fed in as context. It never blocks — a failing build is something for the reviewer to explain, not a reason to skip the review. Unset (the default) changes nothing.
- It's **read-only** — it never fixes or commits. It writes `reviews/<ts>/code-review.md`, prints the findings as JSON after a `===FINDINGS_JSON===` marker, and appends one line to the review log, `~/.agent-config-studio/review-log/review-log.jsonl` (an existing older log under `~/.claude` keeps being used until that folder exists).

**Big diffs: review in slices.** The prompt inlines at most 120k characters of diff; over that, the run warns and names the largest top-level folders.
Slice the one commit instead: run the review once per path group with `REVIEW_PATHS=<pathspec>,<pathspec>` (git pathspecs, comma- or newline-separated; config `paths` also works). A list that matches no changed file is refused.
Each slice gets its own record, findings and close, and a sliced close ignores later changes outside its paths. Commit every fix first, then close every slice at the same HEAD.
**Run the slices in parallel:** `node "$REVIEW_SCRIPT" --slices "<group>;<group>" [--jobs N] "<intent>"` reviews each group (one `REVIEW_PATHS` value, so commas inside a group, `;` between groups) as its own run, at most N at a time (default 4), in this checkout. Each slice prints under `=== slice i/n: <paths> (exit c) ===` as it finishes; then `===SLICES_JSON===` lists `{paths, exit, reviewId, result}` per slice, `result` being that slice's FINDINGS_JSON. A failed slice makes the run exit non-zero: rerun only that group. A big run outlasts a foreground shell timeout, so start it in the background and wait for it to finish. Then fix, fix-check and close each slice by its review id; one HEAD for all the closes is simplest, though a slice closed earlier still counts.
The slices together must cover every file of the diff: the push gate and `--summary` accept them only then, and a missing slice blocks the push and names the uncovered files. Coverage is by content, so a late commit needs only its own files reviewed as one more slice, closed at the tip; the slices closed earlier still count.

**What the push gate accepts.** A changed file is covered when its exact state at the pushed tip (content and mode, or deleted) was seen by a complete close or a clean fix check (one with no finding that needs a status), logged in this repository at a commit the tip descends from. A review on another branch or in another clone covers nothing, and being on the remote already covers nothing. A file whose diff the 120k cap cut is not covered, and a file changed on both sides of a merge needs a review that saw the merge. `builds/` files need no coverage. The tip also needs one complete close at it (or followed only by `builds/` commits), so the tests ran there. A refusal lists the uncovered files: review just those with `REVIEW_PATHS` and close that slice at the tip. Generated dependency lockfiles (package-lock.json, yarn.lock, pnpm-lock.yaml, Cargo.lock, go.sum and the others the gate lists, by exact file name in any folder) are exempt by default; the refusal and `--summary` name every exempt file as not reviewed, so the PR shows them. The operator can list more files in `coverageExempt` (globs, like `riskPaths`) or turn the defaults off with `"coverageExemptDefaults": false`: in the home config (`coverageExempt` also through `REVIEW_COVERAGE_EXEMPT`) or an untracked repo config, never a tracked one. Agents don't add to the list on their own. A refusal for any other file whose diff alone is over the cap goes in the PR as a blocker for the operator, never as a shell command for them to paste.

Parse the `===FINDINGS_JSON===` block (and/or read `reviews/latest/code-review.md`). Keep reviewId and each finding's id for the status file.

## Step 2 — Triage, then fix without asking

The JSON splits three lists: `findings` (quote located), `disputed` (a second opinion REFUTED it, with its evidence) and `unverified` (the quote isn't in the code). Show disputed findings with both sides, and unverified ones as carried unlocated findings with their stored severity. Every non-filed finding in all three lists needs a status at close.

Verify every remaining finding against the actual code before fixing (you have the diff loaded):
- **Keep the scores and derived severity.** The script derives severity from scores; reviewer labels are comparison text only. Scores cannot change in triage.
- **Derived severity.** Reviewers supply likelihood and impact (integers 1–10), protected (boolean) and a concrete trigger. HIGH is protected or risk ≥ 40; LOW is unprotected risk ≤ 10 and is filed; MEDIUM is the rest. Fix HIGH first, then MEDIUM. HIGH, MEDIUM and all unscored findings block until fixed, REFUTED or waived. Invalid scores are re-asked once; still-unscored findings block as MEDIUM (HIGH if protected). Legacy unscored LOW findings also block. Filed findings need no close status, are already decided, and are fixed only when the operator picks them. Grade criterion FAILs stay HIGH and are never filed.
- **Protected cases.** A demonstrated reachable exploit, stored data lost beyond ordinary undo, wrong money, or a way around the review gate in the gate's own logic: the push check, the close, a dispute or a waiver accepting work it should refuse.
  Guard command phrasings (agent-guard) are not protected; score them by likelihood × impact because the guard is an accident barrier.
- **Reject with evidence.** Record a reason and file:line or test evidence. A blocking finding (HIGH, MEDIUM or unscored) rejection needs a REFUTED verdict from --dispute, an earlier REFUTED verdict referenced on the same branch and repository, or an operator waiver. One real verdict per finding; no back-and-forth. NO-VERDICT means it stands and may be retried. If CONFIRMED, fix it. When the reviewer role has only one family, so no second family can give a verdict, only an operator waiver can reject the finding: --waive from a real terminal is the operator's own tool, and agents never ask for it (rule 9).

**Done means:** every non-filed finding has a fixed or rejected status (or, for fix-check and recheck findings, deferred), fixes are committed, and --close succeeds as a complete close at HEAD. Clean reviews close too and run the full tests. A partial close lists outOfScope files and covers nothing.

**No confirmation (rule 10).** Send every HIGH and MEDIUM straight to the fix round, or dispute it with proof; never ask which to fix. A finding that is really a product choice (bug or feature?) gets the safe fix by default and is named in the report so the operator can reverse it. LOWs are filed.

**One report, after the fix round and the fix check:** what was fixed, what was deferred and what was filed, each with its numbers (rule 11), plus any product-choice fix the operator may reverse. Fixing the filed items is optional.

If **no findings survive triage**, still close the review after recording any rejections; a clean report alone is not ready for a PR.

**Log the outcome** optionally for telemetry — confirmed = findings that held up and were fixed, rejected = the rest. --log-outcome is telemetry only; it never closes a review. This is how the unranked pool earns a ranking:
```bash
node "$REVIEW_SCRIPT" --log-outcome <reviews-ts> <confirmed> <rejected>   # e.g. 2026-10-14-11-46-58 2 1
```
For `both`, log each run's folder with its own counts.

## Step 3 — Apply the fixes

If a builder subagent wrote the branch, send it the HIGH and MEDIUM findings and have it fix the **real cause**. Otherwise fix the real cause directly with Edit/Write — you already have the diff loaded. Keep fixes minimal and faithful to the finding; don't suppress or paper over.

Then run the project's linter/formatter on the changed files (whatever the repo uses — e.g. `npm run lint`) and commit the fixes before closing, never after. Fixes never get a full re-review. Write a status file keyed by finding id; unknown keys and any severity field refuse:

```json
{"f1":{"status":"fixed"},"f2":{"status":"rejected","reason":"<why>","evidence":"<file:line or test>","refutedBy":{"review":"<prior review id>","finding":"<prior finding id>"}}}
```

After the fix check, its x… findings (and a Grade recheck's r… findings, or a criterion still failing its recheck) may instead be deferred: `{"x1":{"status":"deferred","reason":"<why>","fix":"<fix idea>"}}`. The reason is required; any severity or score field refuses; an original finding can't be deferred.

Omit refutedBy when using this review's own REFUTED verdict or a waiver. To dispute a serious finding, the orchestrator runs the first command below once for a real verdict. Then close against the committed fixes:

```bash
node "$REVIEW_SCRIPT" --dispute <review-id> <finding-id> --reason "<why>" --evidence "<file:line or test>"
node "$REVIEW_SCRIPT" --close <review-id> --status builds/<slug>/status.json
node "$REVIEW_SCRIPT" --summary
```

Close uses verifyCmd from .claude/review-config.json or --test-cmd. When there are no tests, pass --no-tests "<reason>"; that reason is logged and printed in the summary. If close says a fix check is needed, the orchestrator runs --fix-check <review-id> once, fixes, disputes or defers its x1… findings, then closes. Fixes land before the fix check: commits after it may touch only `builds/` and test files, and close still runs the full tests. A file the fix check saw is in scope at close, so a fix to a sibling file is fine once the fix check has seen it. Close counts a changed file as fixed only when it equals, exactly, the path the script recorded when it checked that finding's quote; a finding with no recorded path (unlocated, ambiguous between a/ or b/ and the bare path, a Grade finding, or one logged before paths were recorded) covers no file. A rename counts as a delete plus an add, so the renamed path is never covered by a finding. A fixed finding covers its whole file, not only the lines it cited. Deal with fix-check findings once (fix, reject or defer each), then a hard stop, with no further model pass. An earlier REFUTED verdict can settle a re-raised finding through refutedBy; do not reopen the dispute without new evidence. Put the --summary output in the PR body. Builders commit at phase end and never run reviews, grades or other models themselves; the orchestrator handles them and opens the PR.

## Review policy (rules 1–11)

1. The operator is involved only at PR merge; no agent pauses work to ask the operator to run a command.
2. First round: every HIGH and MEDIUM from the original review is fixed, or rejected with a REFUTED verdict from a different model (`--dispute`). Nothing is deferred in this round; LOWs are filed automatically.
3. One fix round, then one fix check. What the fix check finds (`x…`, any severity) may be deferred: `{"x1":{"status":"deferred","reason":"<why>","fix":"<fix idea>"}}`. The reason is required, `fix` is optional (the reviewer's suggestion shows otherwise), and the reviewer's score stands. The close then completes; there is no second round.
4. Grade: a criterion still failing after one fix round and its one recheck may be deferred as "criterion not met" with the same status shape, and so may the recheck's own `r…` findings. It never silently passes.
5. The PR body (`--summary`) lists, in order: "Acceptance criteria not met", deferred HIGHs, then all other deferred findings; `--deferred` lists them too. The operator's merge is the approval, and the operator can send the branch back.
   **Merge tier** (`--summary` only reports it; merge.mjs below acts on it). Each close logs a tier, and `--summary` prints `Merge tier: LOW|MEDIUM|HIGH (<reasons>). Policy <policy>: would merge | needs a human`. HIGH: a riskPaths or `merge.alwaysHuman` file (plus `.github/workflows/**` and `package.json`), a deferred HIGH or protected finding, a partial close or `--no-tests`; LOW: nothing deferred and only docs, tests or static files changed; MEDIUM otherwise.
   `merge.policy` is `off` (default: every tier needs a human) | `strict` (LOW, docs and tests only) | `standard` (LOW) | `always` (LOW and MEDIUM; never HIGH). `merge.classifier` (default null) may move only a MEDIUM to LOW at confidence ≥ `merge.threshold` (0.8); on any failure the rules' tier stands, and the record logs `tierBy` and its probabilities.
   A tracked repo config may only make `merge.policy` stricter and cannot set `merge.classifier`; set them in the home config or an untracked repo config.
   **Agent merge.** After opening the PR, the orchestrator runs `node ~/.agent-config-studio/review-gate/merge.mjs` once, always the shared runtime's copy (it uses the repo's `scripts/review.mjs` when there is one; `--pr <n>` names the PR, `--dry-run` only reports). Agents never merge any other way: no `gh pr merge`, no auto-merge, no merge button. It reads `--tier-json` and does one thing: policy `off` does nothing and calls no gh (`none`, exit 0); a tier the policy merges is merged with a merge commit at HEAD (`merged`, exit 0; a merge that only queued or set auto-merge is taken back and needs a human) only when the PR is open, not a draft, its head is local HEAD, its base is the review's base, the tree is clean, GitHub reports no conflict, branch-protection block or requested changes, no `needs-human` label is on it, the base has not moved (`BEHIND`), and every check passes or is skipped; anything else needs a human: `merge.onHuman` `comment` (default) adds the `needs-human` label and one comment (`merge.humanComment`, then the tier line and why), and a PR that already has the label gets no new comment (`labeled`, exit 10); `none` writes nothing (exit 11). A `BLOCKED` PR (branch protection) needs a human. An `UNKNOWN` merge state is read again up to 3 times, 5 seconds apart. An unsafe state (head, base, draft, closed, dirty tree, conflict, still `UNKNOWN`, gh failure, failed merge) is `refused`, exit 2, with no write. Zero CI checks need a human unless `merge.requireChecks` is false; a failing or pending check never merges. `merge.allowBehind: true` lets a `BEHIND` PR merge. A tracked repo config may set `merge.onHuman`, but never `merge.humanComment`, and may only set `merge.requireChecks` to true and `merge.allowBehind` to false. Each run logs an intent and an outcome record to merge-log.jsonl beside the review log. Report the one line it prints; never merge a PR it did not merge.
6. Agents never re-rate a finding (severity and score fields stay refused), defer in the first round, edit, re-log or forge review records, or ask the operator to run `--waive` or `REVIEW_GATE_OVERRIDE`.
7. A history rewrite (squash, split, rebase) after a review or Grade is allowed when the final tree is byte-identical: the gate compares tree hashes with the review, Grade, fix-check, recheck and close heads, and logs the carry-over as `carried`. Any other tree gets a fresh review.
8. An unexpected gate refusal: one fresh review of the final branch through the normal path, then a clean close. If the gate still refuses, stop and tell the operator in chat, quoting the gate's message.
9. `--waive` and `REVIEW_GATE_OVERRIDE` remain the operator's own emergency tools from the operator's terminal; no normal flow uses them.
10. No confirmation before fixing: every HIGH and MEDIUM goes straight to the fix round, or is disputed with proof, without asking. A finding that is really a product choice gets the safe fix by default and is named in the report so the operator can reverse it. The operator hears once, after the fix round and fix check: what was fixed and what was filed. Fixing the filed items is optional.
11. Show the numbers: every finding shown to the operator carries its scores, e.g. `LOW 6/100 (likelihood 2/10 × impact 3/10)`, or `unscored`, never just the word. The report, `--summary` and `--deferred` print them that way.

## Commands (reviewer tiers)

| Command | Reviewer | When |
|---|---|---|
| `/code-review` | The pool pick — **one agent** (no `REVIEW_REVIEWER`; pass `REVIEW_AUTHOR` when known) | The default. Everyday PRs. |
| `/code-review premium` | **The `judge` role's family — ONE agent, one comprehensive pass, never a team** (`REVIEW_REVIEWER=<judge family>`) at its flavor effort | The premium judgment pass. Reserve for changes where being wrong is expensive (payments, order logic, auth, migrations). |
| `/code-review both` | The pool pick, then the `judge` role's family as double-check | Maximum confidence: run both, present ONE merged list — findings both flagged first (near-certain real), then each one's uniques. If the pool pick is already that family, the second run is the first pool family on another vendor. |
| `/code-review claude` | Claude multi-agent team (`REVIEW_REVIEWER=claude`; its lenses run on the reviewer role's Claude families, in role order) — the ONLY multi-agent tier | Only when the user names it. With no Claude family in the reviewer role, it stops and says so. |
| `/code-review <family>` | That family, one agent (`REVIEW_REVIEWER=<family>`) | When the user names one. |

Resolve the judge family with `eval "$(model-id --role judge || echo 'echo "model-id failed: run acs install-model-id (see the Agent Config Studio README)" >&2; exit 1')"` (it sets `family`, `id` and `effort`).

**Plain English works too** — "code review this with <family>", "review it with both" — the phrase picks the tier for that run via the env overrides. These one-run choices never change the durable default (env var → config file → built-in default precedence).

**Auto-routing (when the user doesn't name a tier).** Run `/code-review` with no reviewer named: the script's own rules choose, never model preference — a config `force` rule first (risk paths still force the configured family), then `pick`, then the review config's `routing` (see "Who reviews" and "Routing by size" above). Diff size alone never escalates to premium; **premium** and **both** run when the user names them.
State which reviewer ran and why in one line — the script prints that line. The user's spoken choice always overrides the routing.

For `both`: run the script twice (once with no reviewer named, once with `REVIEW_REVIEWER=<judge family>` — each writes its own `reviews/<ts>/` report), then merge the two findings lists in-context before Step 2. Do not double-fix: one merged list, one fix round.

**The second run double-checks; it does not open a second hunt.** A finding only one model raised survives triage only if it names a concrete trigger (input or call path) you confirm in the code — otherwise record a rejection through the resolution rules above. Never run a third pass to settle a disagreement; settle it with --dispute or the safe fix.

**Effort comes from each family's flavor** in ACS — change it there, not here. For one run: `REVIEW_EFFORT` (codex), `REVIEW_GROK_EFFORT` (grok), `REVIEW_CLAUDE_EFFORT` (a single Claude reviewer), `REVIEW_TEAM_EFFORT` (the claude team).

## Changing the model or reviewer (no script edits)

The skills and the loop **never change** — you swap settings in one small JSON file:

- **All your projects:** `~/.agent-config-studio/review-gate/config.json` (an older `~/.claude/review-config.json` is still read when that file is absent)
- **Just this repo:** `.claude/review-config.json` (per-user; git-ignored). While git tracks it, it can't set `verifyCmd`, `classifier`, `base` or a `pick` that names a command; those are ignored with a warning.

Copy `~/.agent-config-studio/review-gate/review-config.example.json`, rename it to one of the above, and edit the values. Precedence is **env var → that config file → built-in default**, so a quick `REVIEW_MODEL=…` still overrides for one run, and `/code-review claude` switches the reviewer for one run.

- **The pool (default):** leave `reviewer` and `model` out; set `"pick"` (`first` | `rotate` | a family | a classifier command), `"crossFamily"` (`prefer` | `off`), optional `"force"` rules (`[{ "paths": ["<glob>", …] | "risk", "family": "<family>" }]`, first match wins) and `"riskPaths"` (globs: `**` spans directories, `*` stays in one; a pattern with no `/` matches any path segment, like .gitignore). Env: `REVIEW_PICK`, `REVIEW_CROSS_FAMILY`, `REVIEW_AUTHOR`.
- **Second opinion:** `"verify": "second-opinion"` (env `REVIEW_VERIFY`); default off — the quote check always runs. A `reviewer` or `model` key pins a reviewer and bypasses the pool.
- **Who is in the pool, and at what effort:** the `reviewer` role and each family's flavor in ACS (Models → Roles) — never this file. A new model is one registry edit (`model-id --table`).
- **Claude team:** `{ "reviewer": "claude" }` — `claudeModel` `"team"` (the default) runs the lenses on the reviewer role's Claude families; a family name or id in `claudeModel` runs **one comprehensive agent** on that model instead.
- **Optional classifier:** `"classifier": "<command>"` names a local classifier a dispute may ask to choose its verifier; `"pick": "<command>"` lets it choose the reviewer.

Check what's active any time: `node <review.mjs> --show-config` (the repo path `scripts/review.mjs` or the shared `~/.agent-config-studio/review-gate/review.mjs`) — it prints the resolved pool and efforts, pick, crossFamily, the reviewer it would pick and why, the config file, the log path, and reviews logged per family.

Every PR body must include a section titled exactly **Deferred findings**, using the deferred and filed findings in --summary (or `none` when empty). When chasing a bug, first check `node <review.mjs> --deferred` and merged PR descriptions with `gh pr list --state merged --search "Deferred findings in:body"`. Resolve <review.mjs> repo-first, with the shared runtime fallback above. `--deferred` lists this repo by repoId, newest first; add `--all` for every repo. The trigger is the input or call path named in the issue.

Use `node <review.mjs> --rubric` for the current version and score anchors. `~/.agent-config-studio/review-gate/calibration.md` contains the eight reference cases; run `node <review.mjs> --calibrate` (or `--calibrate copy.md`) after rubric changes or when evaluating a new model. Historical log records retain their stored bands and filing decisions.
